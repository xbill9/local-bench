# 3. FIRMWARE

- `dmesg | grep -i firmware` → **no output at all**: no firmware load attempts, successes, or failures logged. There is nothing here needing a blob (no GPU, no Wi-Fi, no discrete NIC firmware needed by `mana`/`hv_netvsc`/`nvme`, which are all para-virtual and load no external firmware files).
- `dpkg -l | grep -iE "firmware|microcode"` → **empty**. No firmware package (`firmware-linux`, `intel-microcode`, etc.) is installed. This is not a gap for a synthetic Hyper-V VM — none of the bound drivers request firmware blobs — but it does mean no microcode update path exists locally.
- **Microcode**: `/proc/cpuinfo` reports `microcode: 0xffffffff` and `dmesg | grep -i microcode` returns nothing. `0xffffffff` is Hyper-V's standard masking value — the hypervisor hides the real host microcode revision from the guest and blocks in-guest microcode loading. This is expected/by-design on Azure, not a fault.

**Instrumentation genuinely ABSENT from this VM (not a missing tool — nothing to observe):**

- **`/sys/class/hwmon`**: does not exist. No hwmon device is registered at all — confirmed by directory absence, not a permissions error. Hyper-V doesn't synthesize a hwmon/sensor device for guests; a bare-metal Xeon host would have one via `coretemp`/platform drivers. This is the **hypervisor not exposing** sensor hardware to the guest, not `lm-sensors` being uninstalled — installing `sensors` here would find nothing to probe.
- **`/sys/class/powercap`** (RAPL): does not exist. RAPL MSRs are a physical-CPU energy-accounting facility that Hyper-V does not virtualize/pass through to guests. Genuine hypervisor restriction — no amount of tooling would recover this without host-level access.
- **`/sys/class/thermal`**: contains only `cooling_device0/1` (Hyper-V's synthetic throttling notification path), **no `thermal_zone*`**. No temperature sensor is exposed to the guest — again the hypervisor hiding physical thermal data, distinguishable from "just not instrumented" because the cooling-device stubs exist but carry no temperature source.
- **`/sys/devices/system/edac`**: does not exist. No ECC/memory-error reporting surfaced to the guest — expected, since DRAM ECC handling is a host/hypervisor responsibility, not delegated to VMs.
- **`/dev/tpm*`**: absent, and IMDS confirms `virtualTpmEnabled: false` for this VM — a real, deliberate configuration choice (vTPM is available on Azure but was not enabled for this instance), not a hidden capability.
- **Real CPU microcode revision**: masked to `0xffffffff` (§3) — Hyper-V intentionally hides the true value; distinguishable from "not supported" because the field exists and is populated, just with the sentinel mask value rather than a real revision or an absent field.
