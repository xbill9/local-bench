# 4. KERNEL ERRORS

- **Taint:** `/proc/sys/kernel/tainted` = `0` — kernel is untainted.
- `dmesg` is short (690 lines total); grepping error/fail/warn and de-duplicating:

| Count | Message | Benign? |
|---|---|---|
| 2 | `GPT: Use GNU Parted to correct GPT errors.` (+ header mismatch lines) | **Benign** — occurs at 1.95s and 2.23s during boot, before `gce-disk-expand` resizes the root partition/moves the GPT backup header to match the new (larger) disk size. Transient, self-corrected by the same boot's disk-expand step. |
| 1 | `unchecked MSR access error: RDMSR from 0xe2` | **Benign** — MSR 0xe2 is `MSR_IA32_MISC_ENABLE` probing for turbo/EIST state; KVM doesn't emulate it and the kernel logs-and-ignores rather than crashing. Standard guest noise. |
| 3 | `systemd-ssh-generator: Failed to query local AF_VSOCK CID` | **Benign** — this generator looks for a VSOCK device (used for host↔guest SSH proxy in some hypervisors, e.g. Firecracker/Cloud Hypervisor); GCP's KVM doesn't expose VSOCK, so the lookup correctly fails and the generator exits — no SSH-over-vsock is expected here. |
| 1 | `i8042: Warning: Keylock active` | **Benign** — cosmetic quirk of QEMU's emulated i8042 PS/2 controller reporting the keyboard-lock line as asserted; irrelevant on a keyboard-less VM. |
| 1 | `RAS: Correctable Errors collector initialized.` | Informational, not an error. |

No ACPI errors/warnings/failures at all (`dmesg | grep -i acpi` combined with err/fail/warn returned nothing). No `dmesg --level=err,crit,alert,emerg` entries beyond the ssh-generator vsock messages already covered.

`journalctl -b -p err` additionally shows:
- `google_guest_agent: Failed to run clock skew setup: failed to run hwclock: fork/exec /sbin/hwclock: no such file or directory` — real but low-impact: the `util-linux` `hwclock` binary isn't installed in this minimal image, so the guest agent's clock-skew-correction helper no-ops. Not consequential since `kvm-clock` (not the RTC) is the active clocksource.
- One `sshd-session: kex_exchange_identification: read: Connection reset by peer` — a single external client (likely an internet scanner hitting the public IP) that reset the TCP connection before completing SSH key exchange. Not a host defect.

# 7. GAPS

Hardware/kernel facilities present but unobservable with the current toolset:

| Present facility | Evidence | Missing tool | Package to install |
|---|---|---|---|
| TPM 2.0 device | `/dev/tpm0`, `/dev/tpmrm0` exist; `tpm_tis MSFT0101:00: 2.0 TPM` in dmesg (Microsoft virtual TPM, i.e. GCP Shielded VM vTPM) | no way to query/attest it | `tpm2-tools` |
| NVMe SMART/health log | `nvme0n1` bound to `nvme` driver, `nvme list` works | `nvme smart-log` works today (nvme-cli present) but generic `smartctl` cross-checking is absent | `smartmontools` (optional, redundant with nvme-cli here) |
| Correctable/uncorrectable memory errors (RAS) | kernel prints `RAS: Correctable Errors collector initialized.` at boot — the collector is active | no consumer of the events (`/sys/devices/system/edac` doesn't even exist — see below) | `rasdaemon` (userspace consumer; won't create the sysfs tree itself — see next point) |
| PCIe hotplug fabric (10 `pcieport` bridges) | `lspci` shows the full switch topology | no `lshw`/`lsusb`-style consolidated hardware summary | `lshw`, `pciutils` extras |
| Network link/driver stats beyond basics | `gve` driver bound | `ethtool` present covers this adequately — not a gap |

Instrumentation absent because the **virtual hardware genuinely doesn't expose it** (not the hypervisor hiding a real capability):
- **`/sys/class/hwmon`** — does not exist. No hardware monitoring chip is emulated by KVM/GCP; a bare-metal box would have this from real voltage/fan/temp sensors. Confirmed absence, not a driver gap — there's no PCI/platform device in `lspci`/`dmesg` that a hwmon driver could bind to.
- **`/sys/class/powercap`** — does not exist, i.e. no RAPL. Emerald Rapids silicon has real RAPL, but KVM does not virtualize the RAPL MSRs/PCI power-management registers to guests, so this is the **hypervisor withholding a real hardware feature**, not the CPU lacking it. (Distinguishable because the CPU flags/model are the genuine Emerald Rapids part, and GCP publicly does not pass through RAPL to standard guest VMs.)
- **`/sys/class/thermal`** — only `cooling_device0/1` exist, no `thermal_zone*`. No temperature sensor is emulated; consistent with there being no `hwmon` either. This is the hypervisor design (VMs have no physical temperature to report), not a masked capability.
- **`/sys/devices/system/edac`** — does not exist. EDAC requires a memory-controller driver bound to real DIMM hardware, which KVM doesn't expose to guests (RAM is just guest-physical pages backed by host memory). Confirmed absent at the sysfs level, so `rasdaemon` would have nothing to read even if installed — the boot-time "RAS: Correctable Errors collector" message refers to the generic MCE-bus collector, not an EDAC driver.
- **Microcode revision** — real value exists on the host but is masked to `0xffffffff` in the guest, per GCP standard practice, confirmed by the metadata's `cpu-platform: Intel Emerald Rapids` string proving the real SKU is known while `/proc/cpuinfo` deliberately obscures the exact revision.

# VERDICT

1. No action required for stability: 0 failed units, untainted kernel, `is-system-running: running`, no service restarts.
2. Everything flagged in `dmesg`/`journalctl` (GPT/disk-expand transient, MSR 0xe2 probe, AF_VSOCK generator, i8042 keylock, one reset SSH handshake) is expected KVM/GCP guest noise — nothing to fix.
3. `hwclock` binary is missing (`util-linux`'s hwclock component), causing `google_guest_agent`'s clock-skew-setup step to fail every boot; install `util-linux`'s hwclock or accept it (kvm-clock is authoritative anyway, so low priority).
4. If SMART/RAS/thermal visibility is wanted for fleet monitoring, install `smartmontools`, `rasdaemon`, `tpm2-tools` — but note RAPL, EDAC, and hwmon/thermal sysfs simply don't exist on this VM class, so no tool will surface them; don't spend effort chasing those.
5. TPM 2.0 (vTPM) is present and completely unmanaged — worth adding `tpm2-tools` if attestation/measured-boot is part of the security posture here.
6. No real driver or firmware gaps exist: every PCI device with a real function has its driver bound, and no firmware load ever fails.
